# 麦克风（音频输入）硬件事实与实现方案

日期：2026-09-15

## 1. 硬件事实（来源：官方 wiki `wiki.lckfb.com/zh-hans/hspi-sf32lb52/` + SiFli SDK）

| 项 | 事实 |
|---|---|
| 麦克风 | **板载集成 MEMS MIC**（核心板自带），另有 `MIC_BIAS`（偏置）与 `MIC_ADC_IN`（输入信号）引到 30pin 排针第 36/37 脚，可外接 |
| 音频 codec | SoC **内部 AUDCODEC**（ADC/DAC，支持 MICBIAS 偏置），HAL 在 `vendor/sifli/chips/drivers/hal/bf0_hal_audcodec.c` |
| MIC 模拟输入脚 | 同芯片官方参考板 `eh-lb52xu` 注释：`PAD_PA09 … // share with MIC` → **PA09 是 codec 的 MIC 输入（模拟）** |
| 音频输出 | `AU_DAC1N_OUT` + 板载 Class-D PA，`PA_42 = Audio_PA_EN` |
| **1.25mm 两针口** | 官方规格：**外接喇叭口（GH-1.25mm，3W/4Ω 或 2W/8Ω）= 输出**，不是麦克风输入 ⚠️ |
| 冲突点 | 我们板 `PA09` 当前被配成 `CTP_RESET`（触摸复位）——与 MIC 共用该脚 |
| 采样率支持 | 8K/11.025K/12K/16K/22.05K/24K/32K/44.1K/48K |

## 2. 构建路径（已确认可行）

- vendor 树的 `chips/sf32lb52/CMakeLists.txt` 用 `file(GLOB HAL_SRCS drivers/hal/*.c)` 后 **显式排除 `bf0_hal_audcodec.c`**；
- 走 Kconfig（`BSP_ENABLE_AUD_CODEC`）不可行：它 `select RT_USING_AUDIO`（RT-Thread 符号，NuttX 树里不存在）；
- **`HAL_DMA_*` 已在固件中**（DMA HAL 正常编译）；
- ⇒ 方案：**把 `bf0_hal_audcodec.c` 加入我们 app 的 `CMakeLists.txt`**（与 `fusion/` 同样做法，自包含于提交仓），应用里直接调 HAL。

## 3. 实现步骤（照官方 SDK 的 RX 范例）

```c
bf0_enable_pll(44100, 1);                                  /* 音频时钟 */
HAL_AUDCODEC_Init(&codec);
HAL_AUDCODEC_Config_RChanel(&codec, 0, codec.Init.adc_cfg);
HAL_AUDCODEC_Receive_DMA(&codec, buf, bufSize, HAL_AUDCODEC_ADC_CH0);
HAL_NVIC_EnableIRQ(AUDCODEC_ADC0_DMA_IRQ);
HAL_AUCODEC_Refgen_Init();
HAL_AUDCODEC_Config_Analog_ADCPath(codec.Init.adc_cfg);
__HAL_AUDCODEC_LP_ENABLE(&codec);
```
外加：
1. `HAL_PIN_Set(PAD_PA09, GPIO_A9, PIN_NOPULL, 1)`（参考板做法：断开数字驱动，让模拟 MIC 输入工作）；
   ⚠️ 触摸复位也用 PA09 → 需要"开机先做触摸复位、录音时切到 MIC"（或用 `--no-touch-reset` 变体验证触摸是否仍可用）。
2. 自己提供 DMA 句柄与中断处理（`AUDCODEC_ADC0_DMA_*`），双缓冲 16 kHz / 16 bit 单声道。
3. 采集 → 环形缓冲 → 通过链路 **新增 `CH_AUDIO` 通道**（设备→PC 方向不受限，实测曾跑通 526 KB 帧）以 DATA 帧上行；
4. PC 侧 `tools/gateway.py` 收到 CH_AUDIO → 存 WAV（便于先"听"验证）→ 再接语音识别。

## 4. 语音联网（下一步，可选）

```
板载 MIC → codec ADC(16k/16bit) → CH_AUDIO 帧 → PC 存 WAV
        → ASR（本地 faster-whisper 或云端 API） → LLM → 答案回传 → 手表 AI 卡片
```
链路与时间同步已就绪（见 `docs/联网功能与串口根因-2026-09-15.md`）。

## 6. bring-up 实测进展（2026-09-15 晚）

**已实现**：`src/mic_audcodec.c|h` 直接驱动内部 AUDCODEC（HAL 已在 arch 库中，无需搬源码），含 DMA 环形缓冲与 RMS/峰值统计；链路在线工具 `!mic`（start/stop/stats/regs/poll/sweep），并加**保活挂钩**（录音路径自动 `pm_report_activity()`，避免 PM SLEEP 门控 codec 时钟）。

**已排除**：
- RCC 模块时钟未开（`HAL_AUDCODEC_MspInit()` 为空）→ 已补 `RCC_MOD_AUDCODEC`/`DMAC1`；
- 官方序列缺项 → 已补 `bf0_enable_pll()` + `Clear_All_Channel` + `ADCPath_Volume`；
- PM SLEEP 导致"无数据"（此前所有测试都在 `[PM] -> SLEEP` 下进行）→ 现测试时系统保持 `[PM] -> ACTIVE`；
- DMA 未武装 → 实测 `ccr=0x2aaf cndtr=1024`（circular，已武装）；
- 12 组时钟配置（src/osr/div/op）全部 `hw irqs=0`、`ADC_CH0_ENTRY` 恒 0；
- 无 fault、无中断风暴（10 s 原始串口观察）。

**当前阻塞点**：寄存器已"看起来全对"（`CFG=1` ADC 使能、`ADC_CFG/CH0_CFG` 已配、PLL 锁定、BG 开、ADC1/2 通路使能），但 **codec 不产生转换数据、也不发 DMA 请求**。

**剩余假设（按性价比排序）**：
1. **数字通道映射**：板载 MIC 可能走 ADC1 → 需试 `channel=1`（`AUDCODEC_ADC1_DMA_REQUEST = DMA_REQUEST_40`；dma_config.h 未给 CH1 的 instance/IRQ，需要试同一 DMAC1 通道或 CH5）。
2. **厂商驱动的最后一步"启动"**：内部 codec 的 RT-Thread 驱动不在公开 SDK（`customer/peripherals/audio/Kconfig` 只有 DA7212）→ 需要 SiFli/LCKFB 提供内部 codec 的初始化范例。
3. **AUDPRC 参与数据搬运**：`ADC_CFG.OP_MODE` 可能要求 AUDPRC 侧使能（试 opmode 与 AUDPRC 配置组合）。

**结论**：软件侧能做的排查已做完；下一步要么继续试 (1)/(3)，要么向 SiFli/立创索要内部 codec 的 bring-up 代码片段，会更省时间。

## 2026-09-19 二轮彻查（读取被排除的 vendor HAL 源码 + 真机变体矩阵）

### 读源码得到的官方路径（`vendor/sifli/chips/drivers/hal/bf0_hal_audcodec_m.c`）
- 我们芯片编译的是 `_m.c`：**单实例** `hwp_audcodec`（无 56x/58x 的 LP/HP 两套，
  52x 头文件里 `AUDCODEC_LP` 出现 0 次）——上一轮以为要配 LP 的方向是错的。
- `HAL_AUDCODEC_Init()` 只做 DMA 句柄初始化；`MspInit()` 是空的；
  `HAL_AUDCODEC_Config_ADCPath()` 在本芯片**未链接**（在 `#endif` 之外），
  且它内部把 ADC 字段写进了 `CFG`（看起来是 vendor 笔误）。
- `Clear_All_Channel(0x2)` 内部会脉冲 `ADC_CFG.PATH_RESET` ✓ 我们已调用。
- `bf0_enable_pll(freq, type)` 是公开的完整上电序列（HXT 音频缓冲 `PMUC_HXT_CR1.BUF_AUD_EN`、
  bandgap、PLL 配置、**VCO 校准循环**、锁检测）——我们已调用（另有一条 `updata_pll_freq()+HAL_TURN_ON_PLL()` 路径）。

### 真机变体矩阵（新增 `!mic try [0..6]`，每项启动后等 500 ms 读样本/ENTRY）
| 变体 | 内容 | 结果 |
|---|---|---|
| v0 | 基线（当前代码） | samples=0 |
| v1 | `CFG |= 3<<ADC_EN_DLY_SEL` | samples=0 |
| v2 | `bf0_enable_pll(49152000,0)` 全流程替代 | samples=0 |
| v3 | 模拟路径放到数字使能**之后** | samples=0 |
| v4 | 复刻 vendor 的 `CFG` 写法 | samples=0 |
| v5/v6 | 上述组合 | samples=0 |
| — | 另试 `RCC_MOD_AUDPRC`(bit20) 门控 | samples=0，且打开后 codec 寄存器块空闲时读回 magic，已回退 |

### 把寄存器 dump 放进 `mic_start()` 内部（关键方法：外部 `!mic regs` 会读到总线 magic）
```
[MicCFG] CFG=00000001 ADC_CFG=00000a41 CH0=00010a9d ANA=0000002e REFGEN=00000005
[MicCFG] ADC1_1=00125ab3 ADC1_2=0000000e ADC2_1=007a5b33 ADC2_2=0000000e
         PLL5=1152d2d2 PLL6=00def7c0 PLL0=5bd4ba00 STAT=00000000 BG0=00001931
```
按 52x 位定义逐项核对（这次都是"正确"的）：
- `CFG.ADC_ENABLE=1`；`ADC_CFG`：OSR=1 / OP_MODE=0 / **PATH_RESET=0** / CLK_SRC=1 / CLK_DIV=10；
- `ADC_CH0_CFG`：ENABLE=1、**DMA_EN=1**、DATA_FORMAT=1(16-bit)；
- 模拟块：`ADC1/2_CFG2=0x0e` → **EN(bit3)=1、RSTB(bit2)=1、CLEAR(bit0)=0** ✓（已使能、已解复位）;
  `REFGEN_CFG` EN=1/BM=1 ✓；`ADC_ANA_CFG` MICBIAS_EN=1 ✓。

### 结论与下一步（唯一剩余嫌疑）
模拟前端与数字配置**逐位核对全部正确**，但仍无转换、无 DMA 请求、`ADC_CHx_ENTRY` 恒 0
→ 嫌疑集中在 **ADC 数字时钟/FSP**：需核对 `PLL_CFG6` 的 `EN_CLK_ADC0/1/2`、
`SEL/DIVA_CLK_ADC*` 与 `sel_clk_adc_source`（我们的模拟配置里 `sel_clk_adc_source=0`），
以及采样率发生器（FSP）是否真的起振；若仍不通，需向 SiFli/立创索取内部 codec 的 bring-up 例程
（公开 SDK 只有 DA7212 外部 codec 驱动，`hwp_audcodec` 在整棵树里**没有第二个使用者**）。

**另一条重要观测**：系统空闲时整个 codec 寄存器块读回 `0xc0dec000`（总线 magic），
说明该模块**随时可能被 PM 门控**——任何 bring-up 观测都必须在 `mic_start()` 内部或保持 PM ACTIVE 时进行。

## 2026-09-19 第三轮：穷举扫描（结论：公开 SDK 内已无可调项）

### 本轮新增的自查与实验
| 项 | 方法 | 结果 |
|---|---|---|
| DMA/IRQ 是否我们的锅 | 在 `mic_start()` 内部读 `CCR/CNDTR` | `CCR.EN=1`、`CNDTR=1024` ✓ **已武装**；150 ms 后 `CNDTR` 不动 ✗ |
| PLL 与模拟路径的先后 | 模拟配置后再开 PLL（`[MicPLL]`） | `updata_pll_freq -> -1`（**锁失败**）⇒ 模拟路径会复位 PLL；改用 `bf0_enable_pll` 返回 0（锁住）但仍无数据 |
| 音频晶振缓冲驱动强度 | 新发现 `PMUC_HXT_CR1.BUF_AUD_STR`（vendor 从不设置） | 拉到最大 `HXT_CR1 1caf4a6f -> 1caf4e6f` ✗ 无变化 |
| 读对的源码 | 这次读的是**本芯片** `_m.c` 版 `Config_Analog_ADCPath`（此前误读多芯片版） | 52x 用 `GC=0x4`（多芯片是 0x1E）；收尾 `CLEAR=0/RSTB=1/VCMST=0` 与我们实测 `0x0e` 一致 ✓ |
| 历史/其它驱动 | vendor 仓库 git 历史、`audio_rttl` 例子依赖的 `drv_audcodec.c` | 树里与历史里**都没有**（只有 HAL），无参照实现 |
| **穷举扫描** | 新增 `!mic sweep2`：`channel{0,1} × 启动顺序{2} × PLL类型{2} × 时钟源{2} × selclk{3} × diva{3} × FSP{4} × opmode{2}` | **1152 组合，0 产生数据** |

### 结论（如实）
- 数字侧/模拟侧/DMA/时钟选择的**所有可写位都已逐位核对正确**，且 1152 组配置穷举无一产生转换；
- 说明缺的不是"某个配置值"，而是**公开 SDK 未包含的前提**（音频时钟/电源域的隐藏使能，或厂商内部 codec 启动流程）。
- **下一步唯一高效路径：向 SiFli / 立创索取内部 codec 的 bring-up 例程**。HAL 注释本身写着
  “need updata **drv_audcodec** if modify this function”，但该驱动不在公开树中。
- 我们保留的 bring-up 工具（对后续对接有用）：`!mic try [0..9]`、`!mic sweep2`、`!mic probe`、
  `!mic regs`（含模拟块/PLL 寄存器）、以及把 dump 放进 `mic_start()` 的做法（外部读会拿到总线 magic `0xc0dec000`）。

## 2026-09-19 第四轮：失败原因分层定位（回答"为什么不行"）

不再"扫参数"，而是把数据通路**逐层拆开、每层独立取证**，定位到底哪一层没工作：

| 层 | 需要满足 | 实测证据 | 判定 |
|---|---|---|---|
| ① 总线/时钟（数字域） | 块可访问 | `ID=0xc0dec000`（ASCII "CODEC000"）✓、`APB_STAT=0`、`IRQ` 可读且非零 | **活的** |
| ② 通道接口 | 通道使能、APB/FIFO 在工作 | `IRQ` bit17 = `ADC_CH0_APB_UF`（**通道欠载**）| **读侧在跑**（该位可能是粘滞标志，故仅作旁证） |
| ③ DMA 通路 | 请求映射正确、通道使能 | `CCR.EN=1`、`CNDTR=1024`，映射与 vendor `dma_config.h` 逐字一致 | **已武装** |
| ④ 寄存器配置 | 全字段合法 | 逐位核对 + **1152 组穷举**（本轮又补 ADC_CH1、两种启动顺序） | **穷尽仍 0 命中** |
| ⑤ 模拟前端 | 调制器有电、有参考 | `ADC1/2_CFG2=0x0e`(EN/RSTB/CLEAR 正确)、`REFGEN_CFG` EN+BM、`ADC_ANA_CFG` MICBIAS_EN，**并补写 `BG_CFG0` 的 `VREF_SEL/MIC_VREF_SEL/EN_AMP/EN_RCFLT`**（vendor 只在其 DAC 路径里写这些） | 写入生效（`0x1931→0x1909/0x1971`）但**仍无样本** ✗ |
| ⑥ 转换时钟 | ΣΔ 采样时钟 | 只能间接推断；`PLL_CAL_RESULT` 恒 0（无法在安全前提下触发校准测量） | **未测** |

**结论（推理而非猜测）**：
1. ① 证明块上电且可访问；③ 证明数据搬运侧无误；④ 证明"没有任何可写配置能改变结果"；
2. 于是失败**必然**落在 ⑤/⑥——**数字域明明在跑（①③），模拟转换前端却不产样本**；
3. ⑤ 的所有已知字段（含 vendor 只在 DAC 路径里写的共享参考）都已补齐并生效，仍无效 → **缺的条件不在 AUDCODEC 寄存器空间内**，
   只能来自**块外**：模拟域的顶层时钟/供电路由，或板级/硬件的未文档化前提；
4. 这与"公开 SDK 里没有第二个 `hwp_audcodec` 使用者、HAL 注释引用了一个不在本树的 `drv_audcodec`"一致：
   **厂商的内部 bring-up 序列里存在我们无法从代码推出的步骤**。

**方法学收获（可复用）**：
- 外部读寄存器会拿到块 ID/总线值 → **所有观测必须放在 `mic_start()` 内部**；
- `IRQ`/`APB_STAT`/`ID` 这三个此前从未读过的寄存器，才是区分"没转换"与"转换了但没搬走"的关键；
- 分层取证 > 盲扫参数：1152 组穷举的价值在于**证明"配置面已穷尽"**，从而把问题锁定到寄存器之外。
