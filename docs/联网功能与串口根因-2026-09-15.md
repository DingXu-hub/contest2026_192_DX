## 1. 硬件事实（先说清边界）

| 事实 | 依据 |
|---|---|
| **没有 WiFi 硬件** | 板级 BSP/defconfig 无任何 WiFi 驱动 |
| **蓝牙是 BLE-only，无法做 BT-PAN** | `.config`：`BT_PERIPHERAL/CENTRAL/BROADCASTER/OBSERVER`、`BT_HCI`，**无 `BT_BREDR`、无 `NET_BLUETOOTH`**；`bt_pan.c` 是 mock |
| 唯一物理链路 = Type-C 上的 **CH340 串口（UART1，1 Mbaud）** | 板级 pinmux："UART1 - debug" |
| SoC 具备 I2S / PDM / 音频 codec HAL，但**全部未启用** | `.config`：`BSP_USING_I2S/PDM`、`BSP_ENABLE_AUD_CODEC`、`DRIVERS_AUDIO` 均未开；板上有 `PA42 // AUDIO_PA_CTRL` 功放控制脚 |

因此"联网"只能是**串口链路**：设备侧跑帧协议，PC 侧跑网关做 DNS/HTTP(S)/LLM 代理。
（若将来要"真 IP 套接字"，可用 SLIP/PPP 承载同一个帧协议，但见 §3 的带宽限制。）

## 2. 三个真实根因（全部实测定位）

### 2.1 NSH 交互 shell 抢占控制台
`/etc/init.d/rcS` 只做 `huangshan_run &`，之后 NSH 的交互会话仍然**读同一个 `/dev/console`**：
- 实测：输入被 shell 执行（`U_: command not found.`），并刷屏 `msh >`；
- 后果：应用与 shell 抢字节 → AI 命令时通时不通。

**修复**：应用启动后接管控制台——`nxsched_foreach()` 找到 `nsh` 任务并 `kill(pid, SIGSTOP)`：
```
[App] console takeover: nsh pid=5 suspended     # 实测，之后 msh 提示符归零
```
（`SIGCONT` 可随时让 shell 回来。）

### 2.2 控制台 RX 等效"1 字节深"，背靠背发送必然丢
实测（发送 63 个递增字符，观察设备回显）：

| 发送方式 | 设备收到 |
|---|---|
| 一次性 63 字节 | 2~19 个，**散落**（如 `QR89bdehjklnqstvwy.`） |
| 每 4 字节一组、间隔 5 ms | **每块只活最后 1 字节**（`DHLPTX159dhlptx`） |
| **每字节间隔 1 ms** | **63/63，零丢失** ✅ |

→ 结论：这条 RX 路径实际只有 ~1 字节缓冲（新字节覆盖旧字节），任何"突发写入"都会被截断。
**这解释了此前所有"命令丢失/首字母被吃/整条不见"的现象。**

**修复（PC 侧）**：网关/测试工具改为**逐字节节流写**（1.2 ms/字节 ≈ 830 B/s）。

### 2.3 帧编码错误（自查发现）
PC 端早期实现把 CRC 算成"仅帧头"或把载荷写了两遍；设备端打印 `hdr ... crc=0xXXXX` + `crc=BAD` 直接定位。
**修复**：统一为 `MAGIC | type ch seq len(2) | CRC16(帧头+载荷) | 载荷`，并加编解码自检。

## 3. 链路协议（`src/link.h`）

```
帧格式（小端）:
  AA 55 | TYPE | CH | SEQ | LEN(2) | CRC16(2) | PAYLOAD(LEN) | PAD(0x0A * n)
CRC16 = CCITT-FALSE(poly 0x1021, init 0xFFFF)，覆盖 TYPE..PAYLOAD
接收端以 AA 55 重同步，忽略帧间填充字节（0x00/0x0A）

TYPE: 0=CTRL 1=TEXT 2=DATA 3=ACK
CH  : 0=CTRL 1=TEXT(AI 协议) 2=HTTP 3=FILE 4=IP(预留,SLIP)
CTRL: 0x01 PING → 0x82 PONG(+uptime) | 0x02 SET_TIME(be32 s + be32 us) | 0x04 WHOAMI
```
- 每个好帧回 ACK；发送方未收到 ACK 就重发（3 次后放弃并把网关标记为离线）。
- 设备端由 `link.c` **独占** `/dev/console`；非帧字节仍按行喂给 AI agent（裸终端兼容）。

实测指标：ACK 6/6，PING RTT ≈ 67–79 ms，`rx_bad` ≤ 1（长时间测试无丢帧）。

**带宽**：受 §2.2 限制，PC→设备 ≈ 830 B/s（节流写），设备→PC 不受限（曾 526 KB 帧 dump 正常）。
因此适合命令/请求/小载荷；大批量下行（固件/大文件）应改为设备侧拉取或分段断点续传。

## 4. 使用方式

```powershell
# 1) 设备已烧录（本仓库 app），NSH 由应用自动接管
# 2) PC 侧启动网关（API key 只走命令行，不入库）
py -3 tools/gateway.py COM4 --api-key sk-xxxx
#    … 然后在网关命令行敲：
!link                     # 查看链路状态
!time                     # 查看/同步时间
!http https://api.github.com/zen
?how should i pace a 5k   # LLM 提问（走 DeepSeek）
```
- 网关启动即 `SET_TIME` + `WHOAMI` + `PING`；设备回 `PONG`/`clock synced`。
- HTTP 结果会打印到串口日志**并作为 AI 卡片显示在手表上**。
- 不做 `SET_TIME` 时时钟保持启动值；`--no-time` 可关闭。

## 6. 遗留与下一步

1. **麦克风**：板级代码零支持（仅 `AUDIO_PA_CTRL`），BSP 有 PDM/I2S/codec HAL 但未启用。
   要继续需要**麦克风型号/接口（I2S 还是 PDM）与接线引脚**，或一张接线照片——据此开启对应通道并写采集驱动。
2. **IP 通道（真套接字）**：`CH_IP` 已预留。可把 SLIP 载荷放进本帧协议（节流写在 830 B/s 下能跑，但慢），或在设备侧用 pppd + 帧承载的字符设备。
3. **文件通道**：`CH_FILE` 已预留（GPX/固件分段传输 + 断点续传）。
4. **反向上行带宽**：设备→PC 不受限，可考虑让设备"拉"大数据。
5. **NSH 恢复**：`kill(pid, SIGCONT)` 可让 shell 回来；若需要调试 shell，可临时注释 `console_takeover()`。
